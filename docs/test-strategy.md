# 订单服务测试策略

## 1. 目标

在服务持续交付的前提下，用可自动执行的测试回答三个问题：

1. **功能是否正确**：鉴权、订单生命周期、金额计算、状态流转是否符合业务规则。
2. **契约是否稳定**：服务端响应是否仍满足消费方约定的字段、类型与枚举。
3. **异常是否可控**：外部支付网关超时、5xx、脏响应时，服务是否按设计降级并保证数据一致。

## 2. 测试范围

### 2.1 纳入范围

| 模块 | 关键行为 |
|---|---|
| 认证 | 正确/错误密码、缺失/伪造/过期/缺少 subject 的 JWT |
| 订单创建 | 必填字段、金额服务端计算、明细落库、状态初始化为 `PENDING` |
| 订单查询 | 详情、404、软删除后不可见 |
| 订单列表 | 状态过滤、客户过滤、分页、排除软删除 |
| 参数校验 | 空明细、数量/单价边界、币种格式、明细数量上限 |
| 取消 | `PENDING → CANCELLED`、重复取消 409 |
| 支付 | 成功 `PAID`、网关 500 → 502 + `FAILED`、超时 → 504 + `FAILED` |
| 删除 | 软删除、记录保留、已支付不可删除 |
| 契约 | JSON Schema、OpenAPI 3.1、Provider/Consumer 字段一致性 |
| 安全基线 | 批量赋值、SQL 注入、畸形 JWT、错误信息泄露、安全响应头 |
| 属性测试 | 金额不变量、商品顺序无关、取消终态、软删除不可见 |

### 2.2 暂不纳入范围

- RBAC、多租户、审计日志；
- 并发下单、幂等键、分布式事务；
- 性能、容量、稳定性压测；
- 完整 OWASP API Top 10、越权/IDOR 与渗透测试（当前只做接口安全基线）；
- 真实支付网关 sandbox 联调。

这些内容在“后续演进”中列出，避免测试范围失控。

## 3. 风险矩阵

| 风险 | 影响 | 可能性 | 优先级 | 对应测试 |
|---|---|---|---|---|
| 未鉴权即可访问订单 | 严重 | 中 | P0 | `tests/api/test_auth.py` |
| 金额计算错误 | 严重 | 中 | P0 | `test_create_order`、数据驱动合法用例、DB 金额断言 |
| 支付超时导致订单状态错误 | 严重 | 高 | P0 | `tests/mock/test_payment_gateway.py` |
| 已支付订单被取消/删除 | 严重 | 中 | P0 | Mock 不可变测试、409 断言 |
| 软删除后仍出现在列表 | 中 | 中 | P1 | CRUD + DB 软删除断言 |
| 响应字段被破坏性修改 | 高 | 中 | P1 | JSON Schema + OpenAPI 字段一致性 |
| 非法参数写入脏数据 | 中 | 高 | P1 | 参数化非法用例 + DB 落库检查 |
| 批量赋值篡改金额/状态 | 严重 | 中 | P0 | `tests/security/test_mass_assignment_is_ignored` |
| SQL 注入导致数据泄露 | 严重 | 中 | P0 | `tests/security/test_sql_injection_is_treated_as_data` |
| 错误响应泄露堆栈/SQL/配置 | 高 | 中 | P1 | `tests/security/test_error_response_does_not_leak_internals` |
| 随机组合下金额计算错误 | 严重 | 中 | P0 | `tests/property/test_total_matches_line_items` |
| 分页/过滤错误 | 中 | 中 | P2 | 列表过滤与分页测试 |
| 第三方 API 行为变化 | 低 | 中 | P3 | 定时 `external_tests` |

## 4. 分层策略

采用“接口层为主、契约层兜底、数据层验证、外部依赖隔离、安全基线守门、属性测试补组合”的组合，而不是单纯追求用例数量。

| 层级 | 目的 | 不做什么 |
|---|---|---|
| HTTP E2E | 验证真实 HTTP 行为、状态码、鉴权、业务规则 | 不重复校验数据库细节 |
| 契约 | 锁定响应结构，拦截破坏性变更 | 不替代业务逻辑断言 |
| DB | 验证写操作真正落库、软删除与状态一致 | 不重复接口层已覆盖的校验 |
| Mock | 覆盖外部依赖异常分支与降级 | 不 Mock 本地服务本身 |
| 安全基线 | 拦截批量赋值、注入、信息泄露等常见风险 | 不冒充完整渗透测试 |
| 属性测试 | 用随机合法数据验证不变量，补人工边界遗漏 | 不替代明确的业务示例 |
| 第三方契约（可选） | 验证公开 API 契约假设 | 不进入主 CI，避免外网抖动 |

### 4.1 测试金字塔的取舍

本项目没有 UI 层，接口层承担主要业务验证；契约层是微服务场景下的“低成本高收益”补充；DB 层只覆盖写路径和状态流转，避免把实现细节全部写死。Mock 层只替换不可控的外部支付网关，保留本地服务、数据库和业务编排的真实性。安全层只覆盖可自动回归的基线风险；属性层用 Hypothesis 自动生成组合数据，失败时收缩到最小反例。

## 5. 测试数据策略

| 策略 | 实现 |
|---|---|
| 数据唯一性 | `uuid4().hex[:8]` 生成客户 ID，避免固定数据冲突 |
| 数据隔离 | 每个 pytest 进程使用独立临时 SQLite 文件 |
| 用例隔离 | autouse fixture 在每个用例结束后清空订单表 |
| 数据与代码分离 | 参数化用例放在 `data/order_cases.yaml` |
| 不依赖生产数据 | 全部数据由 `utils/data_factory.py` 构造 |
| 金额断言 | 使用 `pytest.approx`，避免浮点误差误报 |

## 6. 环境与依赖策略

- 测试启动真实 uvicorn（后台线程），通过空闲端口访问，等待 `/health` 就绪；
- 测试配置在导入 `app` 之前写入环境变量，确保使用独立数据库和假网关地址；
- 支付网关通过 `responses` 在进程内拦截，本地服务通过 `add_passthru` 放行；
- GET 请求允许有限重试，写请求不重试，避免重复下单；
- 所有请求带超时，防止 CI 挂死；
- 支持 `pytest -n auto`，每个 worker 独立数据库与端口。

## 7. 质量门禁

| 门禁 | 标准 | 执行位置 |
|---|---|---|
| 用例通过率 | 100% | CI 每次 push / PR |
| 服务端覆盖率 | ≥ 95% | CI `--cov-fail-under=95` |
| OpenAPI 合法性 | 通过 `openapi-spec-validator` | 契约测试 |
| Provider/Consumer 字段一致 | 必填字段与属性集合一致 | 契约测试 |
| 接口安全基线 | 13 条安全用例全部通过 | CI |
| 属性测试 | 4 条属性 × 25 组随机数据 | CI |
| Dockerfile 可构建 | 构建成功 | CI `docker-build` Job |
| 可选第三方契约 | 定时任务通过 | 每周 schedule |

任一门禁失败即阻断合并（建议在仓库分支保护中把 CI 设为 required check）。

## 8. 缺陷处理约定

| 级别 | 定义 | 处理时限（建议） |
|---|---|---|
| P0 | 鉴权绕过、金额错误、支付状态不一致、数据丢失 | 立即修复，阻断发布 |
| P1 | 主要业务规则错误、契约破坏性变更 | 当版本修复 |
| P2 | 分页/过滤/提示信息错误 | 排入近期迭代 |
| P3 | 第三方 API 波动、非核心边界 | 记录并观察 |

自动化失败时优先判断是“产品缺陷”还是“用例/环境问题”，禁止直接重跑掩盖。Allure 中保留每次 HTTP 请求/响应，便于定位。

## 9. 退出标准

一个版本可以进入发布候选，需要同时满足：

1. 主测试集 87 条用例全部通过；
2. 覆盖率不低于 95%；
3. OpenAPI 文档合法，契约字段一致；
4. 支付异常分支（500/超时/脏响应）均验证为预期降级；
5. 安全基线与属性测试全部通过；
6. 无未关闭的 P0/P1 缺陷；
7. CI 产物（pytest-html、覆盖率、Allure）可追溯。
