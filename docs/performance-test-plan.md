# 性能测试方案（Order API）

> 版本：v1.0　日期：2026-10-26　执行人：彭文涛
> 脚本：`perf/`　结果：`perf/results/`　配套说明：`perf/README.md`

---

## 1. 测试目标

回答四个问题，而不是"跑个 JMeter 截个图"：

1. 当前部署形态下，系统能稳定承载多少并发、多少 RPS？
2. 在预期峰值下，P95/P99 是否满足 SLO？
3. 容量拐点在哪，瓶颈在压测器、网络、应用、数据库还是下游？
4. 优化之后，怎么用同一套脚本证明"真的变好了"？

## 2. 范围

| 纳入 | 不纳入 |
|---|---|
| 登录、创建/查询/列表/取消/支付五个核心接口 | 前端页面性能、CDN、图片加载 |
| 单机单实例部署（uvicorn + SQLite） | 多实例 + 负载均衡 |
| 支付网关用本地替身，验证编排与超时 | 真实网关的限流、抖动、计费 |
| 应用层指标（RPS、RT、错误率） | 服务端 CPU/内存/GC/慢查询（本机无监控组件，列为局限） |

## 3. 指标与 SLO

| 指标 | 目标 | 依据 |
|---|---|---|
| P95 响应时间 | ≤ 500ms | 内部接口经验值；用户可感知卡顿的阈值约 1s |
| P99 响应时间 | ≤ 1,500ms | 长尾容忍度 |
| 错误率 | ≤ 1% | 超过 1% 视为不可用 |
| 5xx | 0 | 服务端错误一律视为缺陷 |
| RPS | 基线 ≥ 40（5 并发） | 以实测基线为准，后续看趋势 |

> SLO 不是拍脑袋：先有基线，再有目标。第一次跑出来的数字就是基线，之后每次对比它。

## 4. 业务模型

按订单服务的真实流量特征建模，而不是均匀压所有接口：

| 动作 | 权重 | 请求 | 说明 |
|---|---:|---|---|
| 创建订单 | 50% | `POST /api/v1/orders` | 主写路径，竞争最激烈 |
| 查询详情 | 20% | `GET /api/v1/orders/{id}` | 读路径 |
| 查询列表 | 15% | `GET /api/v1/orders?customer_id=&limit=20` | 含 `count(*)`，注意分页深翻 |
| 支付 | 10% | `POST /api/v1/orders/{id}/pay` | 同步调用下游 |
| 取消 | 5% | `POST /api/v1/orders/{id}/cancel` | 状态流转 |

**数据模型**：每个虚拟用户独立 `customer_id`，登录一次复用 Token；订单 ID 由用户自己维护，避免读到别人的数据造成假热点。

**思考时间**：`think_time` 为 0–0.2s 随机，模拟真实用户的操作间隔；不用 0，避免把压测器自身 CPU 打满。

## 5. 场景设计

| 场景 | 并发 | 时长 | 爬坡 | 验证什么 |
|---|---:|---:|---:|---|
| smoke | 1 | 10s | 1/s | 脚本与链路自检 |
| baseline | 5 | 30s | 5/s | 建立性能基线 |
| load | 20 | 60s | 5/s | 预期峰值是否满足 SLO |
| stress | 40 | 90s | 2/s | 找容量拐点 |
| spike | 40 | 30s | 40/s | 瞬间流量冲击与恢复 |
| soak | 10 | 300s | 2/s | 长稳：内存/连接泄漏、锁累积 |

**故障注入**：`--gateway-delay-ms 1500` 让支付网关变慢，验证超时降级（订单应转 `FAILED` 并返回 504），这是性能测试里最容易被忽略、但线上最容易出事的分支。

## 6. 环境与数据

| 项 | 配置 |
|---|---|
| 压测机 | 与被测服务同机（Windows 11, Python 3.11.4）——**这是本次最大的局限** |
| 被测服务 | uvicorn 单进程，SQLite 文件库 |
| 数据库 | 每次运行新建独立文件，跑完删除 |
| 下游 | 本地支付网关替身（ThreadingHTTPServer） |
| 网络 | 本机回环，无真实网络延迟 |

生产压测要求：压测机独立、与被测环境同网段、数据量为生产量级的 1/10～1/2、下游用 mock 或沙箱。

## 7. 执行与判定

```bash
python -m perf.run_perf --profile baseline   # 基线
python -m perf.run_perf --profile load       # 峰值
python -m perf.run_perf --profile stress     # 找拐点
```

判定规则写在 `perf/loadgen.py` 的 `THRESHOLDS` 中，不通过则进程退出码为 1，可直接作为 CI 门禁。

## 8. 实测结果

| 场景 | 并发 | 总请求 | RPS | 平均 | P95 | P99 | 错误率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 5 | 1,254 | 41.6 | 19.4ms | 42.5ms | 60.1ms | 0.00% |
| load | 20 | 5,082 | 84.2 | 178.2ms | 637.0ms | 2,148.0ms | 0.04% |
| stress | 40 | 5,060 | 83.7 | 348.3ms | 995.7ms | 2,437.5ms | 0.08% |

**判定**：baseline 通过；load、stress 的 P95 未达标。

**拐点**：并发 20 → 40，RPS 84.2 → 83.7（基本持平），P95 637ms → 996ms（上升 56%）。系统在 ~85 RPS 饱和。

**归因**（按分层排查）：

| 层 | 证据 | 结论 |
|---|---|---|
| 数据库 | 服务端日志 `database is locked`；`create_order` P95 1,039ms vs `get_order` 143ms | SQLite 单写锁串行化写入，是主瓶颈 |
| 应用 | 同步 `def` 接口占用线程池；写等待占满线程后读请求排队 | 线程池与写等待耦合，需隔离读写 |
| 下游 | `pay_order` P95 1,124ms，含网关往返 | 同步调用放大 RT，应改异步回调 + 超时重试 |

## 9. 瓶颈分析方法（可复用）

1. **先看曲线**：`timeseries.csv` 的 TPS 是否随并发线性上升？不升了就是饱和点。
2. **再看分层**：压测器 → 网络 → 应用（线程池/GC）→ 数据库（锁/慢查询）→ 下游（超时/重试）。
3. **对照接口**：读接口正常、写接口慢 → 大概率是锁；所有接口一起慢 → 大概率是应用或机器资源。
4. **验证假设**：改一个变量（如换 PostgreSQL / 加连接池 / 调线程数），用**同一场景**复测，报告自动对比。
5. **不要用平均值下结论**：平均值会掩盖长尾，看 P95/P99 和错误分布。

## 10. 准入准出

- 准入：功能用例全通过、环境稳定、脚本自检通过（smoke）、数据准备完成。
- 准出：load 场景满足 SLO；stress 能找到拐点并有归因；无 5xx；报告归档；优化项有负责人和复测计划。

## 12. 怎么迁移到营销/电商系统（灵狐场景）

同一套方法换成业务模型即可：

- 场景权重按大促/日常分别建模（日常：浏览 60 / 加购 20 / 下单 15 / 支付 5；大促：抢券/秒杀单独成场景）；
- 关键接口换成：活动页配置读取、券领取/核销、订单创建、支付回调、数据回传；
- SLO 换成业务口径：领券接口 P95、下单成功率、支付回调幂等成功率；
- 故障注入重点：券服务超时、库存扣减失败、支付回调重复、第三方平台（抖音/京东）接口限流；
- 数据一致性要在压测后核对：券不能超发、订单与支付流水要平。
